## F1 — Reusable compiled Playwright suites

### Problem
A saved Playwright test can be rerun only one run at a time, by hand, retyping its secrets (V1.1 F5). A team
wants a named set of tests ("checkout smoke") it can run together, again and again, with no model call.

### Design
**Data.**
- `test_suites` (`id` `ste_…`, `tenant_id`, `name` unique per tenant (case-insensitive), `description`,
  `credential_profile_id` nullable → `credential_profiles` on delete set null, `owner_user_id` nullable → `users`
  on delete set null, timestamps).
- `test_suite_entries` (`suite_id` → cascade, `source_run_id` → `test_runs`, `position`, `confirm_destructive`
  boolean, `added_by`, `added_at`; PK `(suite_id, source_run_id)`). At most 50 entries per suite. An entry pins the
  source run: its confirmed requirement and generated test are what a suite run reruns (runs are never deleted,
  only their artifacts expire).
- `suite_runs` (`id` `srn_…`, `tenant_id`, `suite_id`, `suite_name` (copied: the suite may be renamed or deleted),
  `trigger` enum `manual | schedule | api`, `schedule_id` nullable, `owner_user_id` nullable, `context` jsonb (CI
  metadata, F5), `status` enum `RUNNING | COMPLETED`, `verdict` nullable, `created_at`, `finished_at`).
- `test_runs.suite_run_id` nullable → `suite_runs` (index). A child run is an ordinary rerun (`rerunOf` = the
  entry's source run) and appears in history like any other run.

**Ownership.** A suite belongs to its creator. Members see and manage their own suites; admins and the service see
all of the tenant's. A run can be added only by someone who can see it (members: their own runs), so a suite never
exposes another member's test. A suite run and its children belong to whoever triggered it (a schedule's runs to the
schedule's creator).

**Adding a test.** `POST /v1/suites/:suiteId/entries` `{ sourceRunId, confirmDestructiveActions? }`: the run must be
terminal and have a generated test with ≥ 1 compiled criterion and a confirmed requirement (else `409
NOTHING_TO_RERUN`, as V1.1 F5). A run that allowed destructive actions needs `confirmDestructiveActions: true`
(stored on the entry: every later suite run repeats those actions without asking again). Adding a *rerun* adds its
root source instead (the same saved test). The run page gets "Add to suite".

**Running a suite.** `POST /v1/suites/:suiteId/runs` `{ secrets?, credentialProfileId? }` (Idempotency-Key
supported) → `202 { suiteRunId, runIds }`.
- Secrets: the union of every entry's secret names must be covered by, in order of precedence, the request's
  `secrets`, the request's `credentialProfileId`, the suite's credential profile. Else `422 SECRETS_REQUIRED`
  listing the missing names. Each child gets only the names its own source used.
- Every target is re-checked (`422 TARGET_NOT_ALLOWED` naming the entry).
- **Admission (amended):** the suite run takes **one** active-run slot, whatever its size; its children do not
  count towards the cap. Worker concurrency still bounds how many run at once. An empty suite is `409 SUITE_EMPTY`.
- One transaction creates the suite run and every child run (the V1.1 F5 rerun creation, factored out of
  `RerunService` into a reusable `createRerun(tx, …)`), then the children are enqueued in entry order. An enqueue
  failure errors that child (`QUEUE_UNAVAILABLE`, as today) and the others go on.

**Settling.** A suite run is `COMPLETED` once every child is terminal. Its verdict:
- `FAILED` if any child's verdict is `FAILED`;
- else `BLOCKED` if any child is `BLOCKED`;
- else `INCONCLUSIVE` if any child is `INCONCLUSIVE`, `ERRORED` or `CANCELLED`;
- else `PASSED`.
The worker settles it when a child finishes (row lock on the suite run, idempotent); the reaper also sweeps
`RUNNING` suite runs whose children are all terminal (a crash between the two never leaves one open). Cancel:
`POST /v1/suite-runs/:suiteRunId/cancel` cancels every active child.

**Endpoints.** `GET /v1/suites` (`?name=` exact, case-insensitive), `POST /v1/suites` `{ name, description?,
credentialProfileId? }`, `GET /v1/suites/:id` (entries with each source's title, target, secret names, last result),
`PUT /v1/suites/:id`, `DELETE /v1/suites/:id` (its schedules too; its suite runs stay), entries `POST` / `DELETE
/v1/suites/:id/entries/:sourceRunId` / `PUT /v1/suites/:id/entries/order` `{ sourceRunIds }`. `GET
/v1/suites/:id/runs`, `GET /v1/suite-runs/:suiteRunId` (status, verdict, per-child summary), cancel.

**Web.** `/suites` (list, create), `/suites/[id]` (entries with reorder and remove, credential profile, "Run
suite" dialog asking only for secrets nothing covers, recent suite runs, schedules (F3)), `/suite-runs/[id]` (verdict,
children with their verdicts, live until settled). Nav link "Suites". The run page: "Add to suite" on a finished
run with a generated test; "Part of suite run …" on a child.

## F2 — Compare a result to the previous run

### Design
**Lineage.** `test_runs.comparison_key` (text, nullable, indexed with `tenant_id`, `created_at`):
- a rerun (manual or in a suite) inherits its source's key;
- a discovery run with a requirement gets `sha256(targetUrl + "\n" + requirement text, whitespace-collapsed)`;
- a blank-requirement run gets its key when a suggestion is selected (from the selected requirement text);
- runs created before V1.2 are back-filled by the migration with the same rule.

**Baseline.** The previous run is the latest run with the same key, created earlier, `COMPLETED`, and visible to
the caller. `?baseline=<runId>` picks another one (it must be visible and completed; any key).

**Endpoint.** `GET /v1/test-runs/:runId/comparison[?baseline=]` → `{ baseline: TestRunSummary | null, verdict:
{ before, after }, criteria: [{ id, description, critical, before: CriterionStatus | null, after: CriterionStatus
| null, change }], durationMs: { before, after }, costUsd: { before, after } }`. Criteria are matched by id when
their descriptions are equal after normalising whitespace and case, otherwise by description alone; the rest are
`added` / `removed`. `change`: `fixed` (not PASS → PASS), `regressed` (PASS → not PASS), `changed` (other
status change), `unchanged`, `added`, `removed`. A run that is not `COMPLETED` gets `409 RUN_NOT_FINISHED`; no
baseline is `{ baseline: null, … }` with every criterion `added`. A pure `compareResults(before, after)` in the
reporting module does the matching.

**Suite runs.** `GET /v1/suite-runs/:id` gains, per child, `change` against its own previous run (`regressed`
if any critical criterion regressed, `fixed` if the verdict went to PASSED, `unchanged`, `new`) and the suite
run's counts (`regressed`, `fixed`).

**Web and report.** The run page shows "Compared with the previous run" (verdict before → after, changed criteria
first; "Choose another run" picks a baseline from the same key's history). The Markdown report (V1.1 F6) gains a
"Compared with the previous run" section. Suite runs show a change badge per child.

## F3 — Scheduled suite runs

### Design
- Table `suite_schedules` (`id` `sch_…`, `tenant_id`, `suite_id` → cascade, `cron` (5 fields), `timezone` (IANA),
  `enabled`, `created_by` → users set null, `last_fired_at`, `last_suite_run_id`, `last_outcome` (`started` |
  `skipped_running` | `failed:<code>`), timestamps). At most 5 schedules per suite and 50 per tenant.
- Validation with `cron-parser`: five fields only; the time between two firings is at least
  `SCHEDULE_MIN_INTERVAL_MINUTES` (default 15), checked over the next 20 firings. The API returns `nextRunAt`.
- **Firing.** BullMQ job schedulers on a `suite-schedules` queue (`upsertJobScheduler(scheduleId, { pattern, tz })`),
  kept in step with the table: on create / update / delete, and a full resync when the API starts (the table is
  the truth; a lost Redis loses no schedule). The **API** runs the schedule worker, so a firing uses the same suite
  run creation as the endpoint.
- A firing checks, in order: the schedule still exists and is enabled; its creator exists and is not disabled; the
  previous suite run of this schedule has settled (else `skipped_running`); the suite's credential profile covers
  every secret name (else `failed:SECRETS_REQUIRED`); the active-run cap (else `failed:TOO_MANY_ACTIVE_RUNS`). The
  suite run is `trigger: schedule`, owned by the schedule's creator. Each outcome writes an `audit_events` row
  (`schedule.fired`, `schedule.skipped`, `schedule.failed`) and updates `last_outcome`.
- Creating or enabling a schedule refuses a suite whose secrets its credential profile does not cover (`422
  SECRETS_REQUIRED`): a schedule can never be asked for a secret.
- Endpoints: `GET/POST /v1/suites/:suiteId/schedules`, `PUT/DELETE /v1/suite-schedules/:scheduleId`. Permissions
  follow the suite's.
- Web: a "Schedules" section on the suite page (cron with presets — hourly, daily at …, weekdays at … — timezone,
  next run, last outcome, enable switch).

## F4 — API tokens for external triggers

### Design
**Tokens.** Table `api_tokens` (`id` `tok_…`, `tenant_id`, `user_id` → cascade, `name`, `token_hash` SHA-256 unique,
`prefix` (first 8 characters after `tap_`, for display), `scopes` text[], `expires_at` nullable, `last_used_at`,
`revoked_at`, `created_at`). A token is `tap_` + 32 random bytes base64url, shown once. Expiry: 30, 90 (default), 365
days or none. At most 20 live tokens per user. Scopes:

| Scope | Allows |
|---|---|
| `suites:run` | `GET /v1/suites` (to resolve a name), `POST /v1/suites/:id/runs`, `POST /v1/suite-runs/:id/cancel` |
| `results:read` | `GET` a suite run, its JUnit, a test run, its report / `report.md`, its comparison |

**Principal (D6 amended).** The API accepts `X-Api-Token: tap_…` (after the service bearer check, like
`X-Session-Token`; sending both is `400`). A live token gives a user principal with `via: "token"`, `tokenId` and
its `scopes`; the user's role still applies (a member's token sees only their runs and suites). Every route
reachable with a token is listed with its scope in one table in `principal.ts`; any other route is `403
TOKEN_SCOPE`. An unknown, expired or revoked token, or a disabled user, is `401 TOKEN_INVALID`. Disabling a user
revokes their tokens. `last_used_at` is updated at most once a minute per token. Runs and suite runs record the
token (`created_via: { tokenId, name }`) in their stored request / context, and `audit_events` gets
`token.created`, `token.revoked`.

**Endpoints.** `GET /v1/api-tokens` (own; admins `?user=all`), `POST /v1/api-tokens` `{ name, scopes, expiresInDays
| null }` → `{ token, … }` once, `DELETE /v1/api-tokens/:id` (own; admins any). Token management needs a session
(never a token).

**Web path for external callers.** The web app gets `app/api/ext/[...path]` (not the cookie proxy):
- requires `Authorization: Bearer tap_…`, forwards it as `X-Api-Token` alongside the service `API_TOKEN`;
- its own allow-list: only the token-reachable endpoints above; only their query parameters;
- ignores cookies, sets none, does not need an `Origin` (CI is not a browser) and refuses `Sec-Fetch-Site:
  cross-site` (a browser page cannot drive it with a token it doesn't have, but it gains nothing either way);
- checks the Host allow-list like the cookie proxy (`WEB_ALLOWED_HOSTS` must include the public host CI uses);
- rate limit: 120 requests per minute per token prefix (in memory, per web instance; the API also counts per token
  in Redis: 600 per hour → `429`).
The API itself stays private (behind `API_TOKEN`).

**Web.** `/account/tokens`: create (name, scopes, expiry; the token shown once with a copy button), list (prefix,
scopes, last used, expires), revoke. Admins: `/settings/tokens` lists everyone's and can revoke.

## F5 — GitHub Actions integration

### Design
- **JUnit.** `GET /v1/suite-runs/:id/junit.xml` → `application/xml`, a pure `renderJunit(suiteRun, children)`
  (reporting module): one `<testsuite>` per child run, one `<testcase>` per criterion (`FAIL` → `<failure>`,
  `BLOCKED` / `INCONCLUSIVE` → `<skipped message=…>`, non-critical ones named "(non-critical)"). XML-escaped;
  control characters stripped.
- **Client.** `integrations/platform-client/` — a dependency-free ES module (Node ≥ 20, global `fetch`):
  `triggerSuite`, `waitForSuiteRun` (polls `GET /v1/suite-runs/:id` every 10 s, with backoff on 429/5xx),
  `fetchJunit`, `summaryMarkdown` (verdict, children, regressions and fixes from F2, links to the web app). Unit
  tests with Vitest against a fake server.
- **CLI.** `integrations/platform-client/cli.mjs`: `node cli.mjs run-suite --url https://tests.example.com --suite
  "checkout smoke" [--wait] [--timeout-minutes 30] [--junit out.xml] [--fail-on FAILED,BLOCKED,INCONCLUSIVE]`,
  token from `PLATFORM_API_TOKEN`. Exit codes: 0 pass, 1 verdict in `--fail-on` (default `FAILED`), 2 usage or
  platform error, 3 timed out.
- **Action.** `.github/actions/run-suite/action.yml` (`using: node24`, `main: index.mjs`, which imports the client).
  Inputs: `platform-url`, `api-token`, `suite`, `wait` (default true), `timeout-minutes` (30), `fail-on`
  (`FAILED`), `junit-path` (optional). Outputs: `suite-run-id`, `verdict`, `url`. Writes `$GITHUB_STEP_SUMMARY`.
  Sends CI context with the trigger (`repository`, `ref`, `sha`, `runUrl`), shown on the suite run page. The token
  is masked (`::add-mask::`) before anything is logged.
- An example workflow in `docs/operations.md` (and `integrations/README.md`): trigger on `deployment_status`, run
  the suite, upload the JUnit file.
- `POST /v1/suites/:id/runs` accepts `context: { repository?, ref?, sha?, runUrl? }` (short strings; `runUrl`
  must be https).

## Testing

TDD as in V1.1: contracts, repositories, services, routes and the settle / schedule logic get unit or DB-backed
tests; the comparison and JUnit renderers are pure functions with tests; the web path gets proxy tests like
`proxy.test.ts`; web pages get component tests; the client and CLI get tests against a fake server. The E2E suite
(CI mode) gains: a two-test suite run (children rerun with no model call, suite verdict settled), a comparison where a
criterion regresses, a schedule firing (a test hook fires the job immediately), and a token that can trigger and
read but gets `403 TOKEN_SCOPE` elsewhere. `pnpm typecheck`, `pnpm test`, `pnpm test:integration` and `pnpm
test:e2e` green after each feature.

## Risks

- **Tokens are long-lived credentials** that reach the platform from outside: hashed at rest, shown once, scoped
  to triggering and reading, expiring by default, revoked with their user, rate-limited, and the API stays private.
- **Suites repeat destructive actions** without asking again: an entry needs the confirmation once, when it is
  added, and the suite page marks such entries.
- **Schedules consume worker capacity** unattended: one slot per suite run, a minimum interval, a per-tenant
  limit, and no overlap with the schedule's previous run.
- **A pinned test goes stale** as the site changes: that shows up as regressions (F2), which is the point; replacing
  an entry with a newer run of the same test is "Add to suite" on the newer run and removing the old one.
