## F1 — Multi-user login and per-user run ownership

### Problem
V1 has no end-user identity (D6): anyone who reaches the web app can do everything, and a secret-bearing artifact
reveal is only a log line (KI-028).

### Design
**Data.** New tables: `users` (`id`, `tenant_id`, `email` lowercased, unique per tenant, `name`, `password_hash`,
`role` enum `admin | member`, `disabled_at`, timestamps); `user_sessions` (`id`, `user_id`, `token_hash` = SHA-256 of
the token, unique; `created_at`, `expires_at`, `last_seen_at`, `revoked_at`); `audit_events` (`id`, `tenant_id`,
`user_id` nullable, `action`, `run_id` nullable, `detail` jsonb, `created_at`). `test_runs.owner_user_id` (nullable:
runs created by the service token or before V1.1).

**Passwords.** scrypt (N=2^15, r=8, p=1, 16-byte salt, 64-byte key), stored as
`scrypt$<N>$<r>$<p>$<salt b64>$<hash b64>`, compared with `timingSafeEqual`. 10–200 characters. An unknown e-mail
still runs one scrypt (a fixed dummy hash) so response time does not reveal which e-mails exist.

**Sessions.** A login returns a random 32-byte token (base64url) once; only its hash is stored. Lifetime
`SESSION_TTL_HOURS` (default 12, fixed from creation). Logout revokes it. Disabling a user or changing their password
revokes all their sessions. Failed logins: at most 10 per e-mail per 15 minutes (Redis counter), then `429
TOO_MANY_ATTEMPTS`.

**API principal.** The bearer `API_TOKEN` stays required on every `/v1` route (the API is internal; the web server
holds the token). On top of it:
- `X-Session-Token: <token>` → a **user principal** (`{ kind: "user", userId, tenantId, role, name, email }`); a
  missing, expired, revoked or disabled session → `401 SESSION_INVALID`.
- No header → the **service principal** (scripts, the E2E suite, the demos): unrestricted, like V1.

**Authorization.**

| Resource | member | admin / service |
|---|---|---|
| Runs they own (create, view, events, criteria, suggestions, cancel, report, artifacts, rerun) | yes | yes |
| Other users' runs, runs with no owner | 404 (indistinguishable from missing) | yes |
| `GET /v1/test-runs` | own runs only | `?owner=me` or `?owner=all` (default `all`) |
| LLM settings | read | read / write |
| Users | own account (`/v1/auth/*`) | manage |
| Credential profiles (F4) | list and use | manage |
| Test-data sets (F3) | list, use, manage | same |
| Usage (F7) | own runs | tenant-wide, `?owner=me` |
| Exploration cache clear (F8) | no | yes |

Run summaries gain `owner: { id, name } | null`.

**Endpoints.** `POST /v1/auth/login` `{ email, password }` → `{ token, expiresAt, user }`; `POST /v1/auth/logout`;
`GET /v1/auth/me`; `PUT /v1/auth/password` `{ currentPassword, newPassword }`; admin: `GET /v1/users`, `POST
/v1/users` `{ email, name, password, role }`, `PATCH /v1/users/:userId` `{ name?, role?, disabled?, password? }`. An
admin cannot disable or demote themselves (409), so a tenant always keeps an admin. Login, logout and auth routes do
not need a session; every other route takes the principal as above.

**Bootstrap.** With `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` set, the API creates that admin at start
if the tenant has no user. Compose sets `admin@example.com` / `admin-password-change-me`; production refuses that
password (like the dev API token, A13).

**Audit (closes KI-028).** `audit_events` rows for: artifact reveal (with run and artifact id), login success and
failure (e-mail hash, not the e-mail, on failure), logout, user created / changed, LLM settings changes, credential
profile changes, cache cleared. `ApiDeps.audit` is replaced by an `AuditLog` port the routes call; the pino line
stays.

**Web.** The proxy (Ruling R49) now requires a session cookie `platform_session` (httpOnly, `SameSite=Lax`, `Secure`
when the request's origin is https, `Path=/`) for every endpoint except `POST /v1/auth/login`, and forwards it as
`X-Session-Token`. On login the proxy takes the token from the API's answer, sets the cookie and returns the answer
without the token; on logout (and on any `401 SESSION_INVALID`) it clears the cookie. Pages: `middleware.ts`
redirects to `/login?next=…` when the cookie is absent (the API still decides validity). New pages: `/login`,
`/settings/users` (admin), `/account` (change password). The header shows the user's name and "Sign out". History:
an "Owner" column and, for admins, "My runs / Everyone's".

## F2 — Critical / non-critical criterion weighting

- `AcceptanceCriterion.critical: boolean`, default `true` (every persisted requirement stays all-critical). The
  requirement refine gains: at least one criterion is critical. The requirement compiler (model) never sets it:
  every proposed criterion is critical; the user marks non-critical ones in review.
- Review (`PUT /v1/test-runs/:runId/criteria`): toggling `critical` is allowed without a check edit and keeps the
  wording (A7 unchanged otherwise).
- **Verdict (Section 2.4, amended):** the precedence rules apply to the critical criteria only. Non-critical results
  are reported with their status and never change the verdict. `aggregateVerdict` takes `{ status, critical }`.
- `CriterionResult.critical` (default `true` when absent). `TestReport.summary.nonCritical = { total, notPassed }`.
- UI: a "Critical" switch per criterion in review; a "Non-critical" tag on report rows and history-independent
  summary note "N non-critical criteria did not pass; they don't affect the verdict".

## F3 — Reusable test-data sets

- Table `test_data_sets` (`id`, `tenant_id`, `name` unique per tenant, `values` jsonb, `created_by`, timestamps).
  Values: the create request's test-data schema (≤ 50 entries, same key and value rules).
- `GET/POST /v1/test-data-sets`, `GET/PUT/DELETE /v1/test-data-sets/:id`. Test data is not secret (use a credential
  profile for passwords); values are returned.
- `CreateTestRunRequest.testDataSetId?`: the API merges `{ ...set.values, ...request.testData }` (the request wins),
  checks ≤ 50 entries, and stores the merged map plus `testDataSet: { id, name }` in the stored request, so later
  edits of the set never change a created run. Unknown id → `422 TEST_DATA_SET_NOT_FOUND`.
- UI: Settings → Test data (list, create, edit, delete); the new-test form gets a "Test data set" select showing the
  keys it adds.

## F4 — Saved credential profiles

- Tables `credential_profiles` (`id`, `tenant_id`, `name` unique per tenant, `description`, `created_by`,
  timestamps) and `credential_profile_secrets` (`profile_id`, `name`, `ciphertext`, `iv`, `auth_tag`, `updated_at`;
  PK `(profile_id, name)`), AES-256-GCM with AAD `["credential-profile", tenantId, profileId, name]`.
- `GET /v1/credential-profiles` (id, name, description, secret **names**, updatedAt — never values), admin: `POST`
  `{ name, description?, secrets }`, `PUT /:id` `{ name?, description?, secrets?: { name: value | null } }` (null
  removes, omitted names are kept), `DELETE /:id`. Same secret-name and value rules as a run (≤ 10).
- `CreateTestRunRequest.credentialProfileId?`. **D7 amended:** at run creation, and only then, the API decrypts the
  profile's values and stores them as the run's own secrets (encrypted with the run's AAD, fingerprinted), exactly
  like secrets typed into the request. The request's own secrets win on a name clash; together ≤ 10. The worker, the
  purge at run end and redaction are unchanged; later profile edits never reach a created run. The stored request
  records `credentialProfile: { id, name }`. Unknown id → `422 CREDENTIAL_PROFILE_NOT_FOUND`.
- UI: Settings → Credentials (admin), new-test form "Saved credentials" select listing the names it provides.

## F5 — Manual rerun

- `POST /v1/test-runs/:runId/rerun` `{ secrets?, credentialProfileId? }` (Idempotency-Key supported) → `202` with the
  **new** run's id. The source must be terminal and have a generated test with ≥ 1 compiled criterion (else `409
  NOTHING_TO_RERUN`). Every secret name the source run had must be supplied again (its values were purged at its
  end) → otherwise `422 SECRETS_REQUIRED` listing the names. The target is re-checked (`422 TARGET_NOT_ALLOWED`), and
  the active-run cap applies.
- The new run: `kind: "rerun"`, `sourceRunId`, the source's stored request (requirement, test data, options,
  environment, model — for display only), owner = the caller. Its confirmed requirement revision and generated test
  are copied from the source at creation.
- Lifecycle edge `QUEUED → RUNNING_PLAYWRIGHT`. Worker job `rerun-run`: `RUNNING_PLAYWRIGHT` (the real rerun stage:
  sandbox, egress proxy, secrets from `SECRET_*`, scrubbed evidence) → `GENERATING_REPORT` → `COMPLETED`. No model
  client is built and no model call is made. Budget: `maxRunSeconds`.
- **Statuses (D2 amended for rerun-only runs):** per compiled criterion, `PASSED` → `PASS`, `ASSERTION_FAILED` →
  `FAIL` (both `verdictSource: PLAYWRIGHT_RERUN`); `NOT_REACHED` / `UNAVAILABLE` → `INCONCLUSIVE /
  RERUN_NOT_REACHED`; a criterion not in the generated test → `INCONCLUSIVE / NOT_IN_GENERATED_TEST`. A rerun that
  ERRORs leaves its compiled criteria `INCONCLUSIVE / RERUN_NOT_REACHED` (the run still completes: the infrastructure
  failure is in `playwright.status`). No PASS without the rerun's own assertion.
- Summary and report gain `kind` and `sourceRunId`. UI: "Rerun test" on a finished run with a generated test (a
  dialog asks for the needed secrets or a saved profile), and "Rerun of …" on the new run.

## F6 — Downloadable report

- `GET /v1/test-runs/:runId/report.md` → `text/markdown; charset=utf-8`, `Content-Disposition: attachment;
  filename="report-<runId>.md"`. Rendered by a pure `renderReportMarkdown(report)` (reporting module): verdict,
  summary, each criterion (status, critical, how it was confirmed, expected / actual, reason), diagnostics, the
  generated test's source, usage. Table cells and inline text are escaped; the source sits in a fenced block whose
  fence is longer than any backtick run in it.
- PDF: the browser's own print-to-PDF — `/runs/<runId>/print` renders the report with a print stylesheet and opens
  the print dialog. No server-side PDF engine (it would need fonts for every script a requirement can be written in).

## F7 — Cost dashboard

- `GET /v1/usage?from=YYYY-MM-DD&to=YYYY-MM-DD&owner=me|all` (default: the last 30 days, UTC; ≤ 366 days) →
  `{ from, to, totals: { runs, llmCalls, inputTokens, outputTokens, estimatedCostUsd }, byDay[], byModel[], byStage[],
  topRuns[10] }`, from `llm_calls` joined to the tenant's runs (members: their own runs).
- Web `/usage`: totals, a daily cost bar chart (inline SVG), cost by model and by stage, the most expensive runs.
  Nav link "Usage".

## F8 — Persisted exploration cache

Stagehand's cache works only on Browserbase (A3). V1.1 caches the executor's **element lookups** (`observe`), not
model extractions (facts are page values and must be read every run).

- Table `exploration_cache` (`tenant_id`, `key` = SHA-256 of `origin + pathname + "\n" + redacted instruction`; the
  query and fragment are never part of it, `origin`, `path`, `entry` jsonb `{ selector, description, element:
  ElementRef }`, `hits`, `created_at`, `last_used_at`; PK `(tenant_id, key)`).
- Executor `locate`: on a hit, the cached selector must match exactly one element whose recorded chosen locator
  equals the cached one; then no `observe` runs (the recorded step has `llm.cacheHit: true`, zero tokens). Anything
  else is a miss and falls back to `observe`. The destructive-action policy still checks the element either way.
- Writes happen only after the planned step using the element **succeeded** (a failed or blocked attempt never
  populates the cache), which limits what a prompt-injected page can plant.
- `RunOptions.useExplorationCache` (default `true`). Entries unused for 30 days are deleted by the retention job.
  `DELETE /v1/exploration-cache` (admin) clears the tenant's cache; a button in Settings.

## F9 — Multiple scenarios per run

- `TestScenario.id` `SC-1` … `SC-5`; `TestPlan.scenarios` 1–5 (unique ids; ≤ 50 steps each, ≤ 100 in total; step ids
  `PS-n` unique across the plan). **D12 amended.**
- Planner output: `{ scenarios: [{ title, steps }], stopConditions }`. Prompt: one scenario unless criteria need
  different starting states (e.g. logged out vs logged in) or one would undo another's preconditions. Validation
  applies across the plan: every checkpoint captured exactly once; ordered checkpoint pairs in the same scenario and
  in order; ≤ 1 login step per scenario. A scenario's `criterionIds` are those its steps serve or whose checkpoints
  it captures. Blocking and truncation apply per scenario.
- `ExplorationStep.scenarioId` (default `SC-1`). The executor runs scenarios in order, each from a clean session
  (cookies, local and session storage cleared, then the target URL). A failed or blocked step ends **its** scenario;
  the step limit, the budget, cancel and the deadline end exploration. `ExplorationOutcome.scenarioStops` records
  each scenario's stop reason; the verifier uses the stop reason of the criterion's scenario.
- Compiler: one Playwright `test()` per scenario with compiled criteria, each opening the target URL in a fresh
  context (Playwright's default), so a hard failure in one scenario never hides another's criteria. The rerun's result
  parser already keys on `[AC-n]` step titles.
- The fake engine keeps one scenario. UI: "Plan created with N steps in M scenarios".

## Testing

tests; engine changes get pure tests; web changes get component tests; the E2E suite (CI mode) gains: login and
ownership (a member cannot see another member's run), a manual rerun of a PASS run (no model call, rerun-confirmed
PASS), a credential profile run, and a two-scenario plan. `pnpm typecheck`, `pnpm test`, `pnpm test:integration` and
`pnpm test:e2e` green after each feature.

## Risks

- Session cookies make the web app a credentialed target: `SameSite=Lax`, Origin checks on every mutating request
  (already in the proxy), httpOnly cookie, no token in any page.
- Credential profiles keep production credentials at rest (encrypted) for as long as they exist; only admins manage
  them, and each use is recorded in the run's stored request.
- The exploration cache replays an element chosen on an earlier run; verification against the recorded locator and
  success-only writes limit, but do not remove, the chance of a stale or planted element.
- Multi-scenario plans change the planner's output format: the planner eval must be re-run on every offered model.
